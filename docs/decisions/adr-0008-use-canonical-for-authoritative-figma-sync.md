# ADR-0008: Use Canonical For Authoritative Figma Sync

## Context

The Figma synchronization process accepts only a verified `main` artifact,
publishes the reviewed visual state, writes metadata last, and establishes the
baseline for later planning. The previous term `official` did not express that
authority precisely and was overloaded with its vendor meaning in phrases such
as "official Kotlin MCP SDK".

The distinction must remain executable across Kotlin types, Gradle tasks,
TeamCity parameters, runner manifests, generated file names, TypeScript
configuration, documentation, and the derived Figma publication.

## Decision

Use `canonical` for every identifier and description that belongs to the
authoritative `main` Figma Sync process. This includes:

- `CanonicalFigmaSyncScope`, `CanonicalMcpRunnerGenerator`, and canonical
  artifact contracts;
- Gradle tasks such as `prepareCanonicalFigmaSync` and
  `validateCanonicalFigmaArtifactSet`;
- `FIGMA_DOCUMENTATION_SYNC_CANONICAL`, `CANONICAL_STAGING_NAMESPACE`, and
  other configuration keys owned by the process;
- runner `mode=canonical`, `allowCanonicalSections`, and
  `10-canonical-sync-payload.png`;
- references to the canonical model, artifact, runner, metadata, publication,
  and baseline in documentation and Figma.

Reserve `official` for assets or technology supplied by an external owner,
such as the official Kotlin MCP SDK, KtLint's official code style, or official
brand assets.

The rename changed serialized contracts. At the time of this decision, writer
project configuration used schema version `2`; it has since evolved under its
own versioned contract. Executable runner manifests use schema version `4`.
Artifacts with the previous names or schemas are not canonical inputs and must
be regenerated by the TeamCity `Figma Sync` pipeline.

## Consequences

- Names now communicate source-of-truth authority instead of organizational
  approval.
- Vendor-provided technology remains distinguishable from repository-owned
  publication policy.
- TeamCity settings, local commands, fixtures, and integrations must use the
  new names atomically.
- Existing runner manifests, checkpoints, and payload names are intentionally
  incompatible. Recovery requires a fresh full canonical run; maintainers must
  not hand-edit old artifacts to bypass the schema boundary.

## Alternatives

- `authoritative` was accurate but produced longer and less idiomatic API
  names.
- `production` implied a deployment environment that Figma documentation does
  not have.
- `trunk` described the source branch but not validation, publication, or
  baseline authority.
- Keeping `official` preserved compatibility but retained the ambiguity with
  vendor-provided SDKs and assets.

## Supersession

None.
